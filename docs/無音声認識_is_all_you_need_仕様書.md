## 1. 目的・スコープ

### 1.1 目的
キーボード入力・音声認識（ASR）に代わり、口の動き・表情・視線・ジェスチャー・手話をカメラで認識することで、**音を発せず、手を使わずにPC・人とコミュニケーションできるインターフェース**を実現する。

### 1.2 スコープ
- 対象：カメラ映像から複数の非音声モダリティを認識し、共通の意図・テキスト表現に変換し、テキスト表示およびTTS音声として出力する一連のシステム。
- 対象外：本イベント（1日開催）内では、商用レベルの認識精度・セキュリティ・大規模運用は対象としない。プロトタイプとしての動作実証を範囲とする。

### 1.3 対応テーマ
「地域・社会課題の解決」を主テーマとし、「個人の生産性を高めるツール」の側面も併せ持つ。

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| 無音声認識 | 音声を発さず、口の動き・表情・視線・ジェスチャー・手話等の視覚情報から発話意図を認識すること |

## 3. 背景・課題

### 3.1 現状の課題
現在のPCとのコミュニケーション手段（キーボード、音声認識）は、以下3条件を前提としている。

1. 手が使える（キーボード・マウス操作が可能）
2. 声を出せる（発話可能な環境・身体条件）
3. 音が聞こえる（相手の発話を聴覚で受け取れる）

この前提が崩れる場面（騒音環境、発話不可な場所、聴覚障害等）では、既存インターフェースが機能しない。

### 3.2 社会的背景
- オンライン会議の普及により場所を問わず会話できる一方、騒がしい場所・声を出せない場所からの参加は困難。
- 聴覚障害には多様なケースが存在する（手話を第一言語とする人／中途失聴等で手話を習得していない人）。既存の音声認識・手話認識はそれぞれ個別最適化されており、統一的な入力手段が存在しない。

### 3.3 課題設定
入力方法の違いをAIが吸収し、誰もが自分に合った方法で入力でき、相手には統一された形で伝わる共通インターフェースを実現する。

## 5. システムアーキテクチャ

### 5.1 全体構成

```
[入力層] カメラ / センサー
    │
    ├─ 口の動き（無音発話・リップリーディング）
    ├─ 表情
    ├─ 視線
    ├─ ジェスチャー
    └─ 手話
    ▼
[認識層] モダリティ別認識モデル
    ▼
[意図統合層] 認識結果を共通の意図・テキスト表現に変換
    ▼
[翻訳層（任意）] 多言語翻訳
    ▼
[出力層]
    ├─ テキスト表示（画面・字幕）
    ├─ TTS音声出力
    └─ PCコマンド出力（アプリ操作・会議ツール連携）
```

### 5.2 レイヤー仕様

| レイヤー | 入力 | 処理内容 | 出力 |
|---|---|---|---|
| 入力層 | カメラ映像 | 映像取得・前処理（顔検出、フレーム抽出等） | 正規化された映像フレーム |
| 認識層 | 映像フレーム | モダリティ別に特徴抽出・分類/系列認識 | モダリティごとの認識候補（テキスト/ラベル＋信頼度） |
| 意図統合層 | 認識候補（複数モダリティ） | 信頼度に基づく統合、共通フォーマットへの変換 | 統合テキスト（発話意図） |
| 翻訳層 | 統合テキスト＋対象言語 | 機械翻訳 | 翻訳後テキスト |
| 出力層 | 最終テキスト | 画面描画／音声合成／コマンド解釈 | 字幕表示／音声／アプリ操作 |

## 6. 機能要件

要求IDごとに優先度（Must＝必須／Should＝推奨／Could＝余力があれば）と受け入れ基準を定義する。

| ID | 機能名 | 内容 | 優先度 | 受け入れ基準 |
|---|---|---|---|---|
| FR-01 | 口パク（無音発話）認識 | カメラで口唇の動きを取得し、発話内容をテキスト化する | Must | あらかじめ定めた短いフレーズ（数語〜一文）を無音で発話した際、テキストとして画面に表示される |
| FR-02 | 表情認識 | 表情から簡易的な意図（Yes/No、感情等）を推定する | Must | 「はい」「いいえ」に相当する表情を提示した際、対応する結果が表示される |
| FR-03 | ジェスチャー認識 | 手や体の動きから定型コマンド・意図を認識する | Must | あらかじめ定めた1〜数種類のジェスチャーが、対応する意図として認識される |
| FR-04 | テキスト出力 | 認識結果を画面上にリアルタイム表示する | Must | 入力からテキスト表示までの遅延が体感で会話として成立する範囲（目安2秒以内）である |
| FR-05 | TTS音声出力 | 認識・変換されたテキストを音声合成で出力する | Must | テキスト確定後、対応する音声が再生される |
| FR-06 | 視線認識 | 視線移動によるポインティング・選択操作 | Should | 画面上の選択肢を視線移動により選択できる |
| FR-07 | 手話認識 | 手話の単語・簡易文をテキストに変換する | Should | あらかじめ定めた手話単語（数語）が対応するテキストとして認識される |
| FR-08 | 多言語翻訳 | 認識結果を任意の言語に翻訳して出力する | Should | 認識されたテキストが指定言語に翻訳されて表示・音声出力される |
| FR-09 | PCコマンド連携 | 認識した意図をPC操作（アプリ起動、会議ミュート解除等）に変換する | Could | 定めたコマンド（1〜数種）が対応するPC操作として実行される |
| FR-10 | 双方向モード | 自分は無音入力、相手には音声出力という非対称コミュニケーションを実現する | Could | 送信側が無音で入力した内容が、受信側に音声として届く |

## 7. 非機能要件

| ID | 項目 | 要件内容 |
|---|---|---|
| NFR-01 | リアルタイム性 | 入力から出力までの遅延は、会話として成立する範囲（目安1〜2秒以内）を目標とする |
| NFR-02 | 環境耐性 | 一般的な室内照度・多少の背景ノイズがある環境下でも動作すること（暗所・逆光等の極端な条件は対象外） |
| NFR-03 | プライバシー | カメラ映像の保存有無・処理場所（ローカル／クラウド）を明示し、必要以上のデータを保持しない |
| NFR-04 | 拡張性 | 新しい入力モダリティ・対応言語を追加できるよう、モジュールを疎結合に設計する |
| NFR-05 | デモ再現性 | イベント当日、複数回のデモ実施に耐えられる安定動作を確保する |

## 8. 開発方針：Codexの活用とAI-DLC

### 8.1 Codexの位置づけ
Codexは単なるコード生成ツールではなく、開発プロセス全体を推進する協働エージェントとして位置づける。

| 開発タスク | Codexの役割 | 人間の役割 |
|---|---|---|
| 認識モデルのプロトタイピング | モデル構造の叩き台生成、複数手法の並行試作 | 採用するアプローチの選定 |
| データ収集・前処理ツール | 収集・ラベリング・前処理スクリプトの生成 | 収集対象データの定義 |
| モダリティ統合ロジック | 統合レイヤーの実装・リファクタリング | 統合ルール（優先度、閾値等）の設計判断 |
| デバッグ・改善 | 原因切り分け、ログ分析、反復修正 | 精度・挙動の受け入れ判断 |
| UI・出力層実装 | テキスト表示、TTS連携、翻訳API連携の実装 | UI要件・体験フローの決定 |

### 8.2 AI-DLCに基づく開発プロセス

AI-DLC（AI-Driven Development Life Cycle）の考え方に基づき、「意図の明確化 → Codexによる実装・試行 → 人間による検証・承認」の短いサイクルを、Inception（構想）／Construction（構築）／Operations（検証・仕上げ）の3フェーズで回す。9:00〜21:00の1日開催に合わせたタイムラインを以下に定める。

| フェーズ | 時間目安 | 内容 | 承認ゲート |
|---|---|---|---|
| Inception | 9:00〜10:30 | MVPスコープの最終決定（FR-01〜FR-05中心）、デモシナリオの選定、Codexによる技術方針の壁打ち | チームでスコープ・構成を合意 |
| Construction | 10:30〜18:00 | 30分〜1時間単位のサイクルで「Codexに実装させる→動作確認→次の指示」を反復。データ収集基盤構築→各モダリティのモデル試作→統合・出力層実装の順に着手 | 各サイクル終了時に人間が動作を確認 |
| Operations | 18:00〜21:00 | 想定シーン（S-1, S-2）に近い条件でのE2E動作検証、デモシナリオ確定、ピッチ資料の最終化 | デモが安定動作することを確認 |

### 8.3 プロセス運用上の原則
- 人間はCodexの出力の消費者ではなく監督者として、都度動作確認し次の指示にフィードバックする。
- モデル系タスクは一度で精度が出ないことを前提に、反復回数を確保する時間配分とする。
- どの設計判断を人間が行い、どの実装をCodexに任せたかを記録し、審査基準「Codexの効果的な活用」の説明材料とする。

## 13. まとめ

音声認識の次のインターフェースとして、音や手に依存しないコミュニケーション手段を提案する。口パク・表情・視線・ジェスチャー・手話という多様な入力方法をAIが吸収し、誰もが自分に合った方法で入力し、相手には統一された形（テキスト・音声）で伝わる仕組みを、ハードウェアからAIモデルまで一気通貫で開発する。

開発にあたってはCodexをAI-DLCの考え方に沿って開発プロセス全体の協働者として位置づけ、人間は課題設定・設計判断・検証に集中しながら、Inception→Construction→Operationsの短いサイクルを1日で回すことで、実際に動くプロトタイプとして完成させる。
