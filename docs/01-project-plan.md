# モデル選定の進め方

更新：2026-09-08。最新の依頼に合わせ、当面は既存VSR・手話モデルの試運転と選定を行う。

## 現在の目的

論文上の数値だけで決めず、「取得できるか」「自分たちの環境で動くか」「何が返るか」「使えそうか」を確かめる。
英語VSRはVALLRとLipCoordNetを検証候補とする。手話は対象言語と実演可能者を確認して候補を絞る。
モデルの最終採用、GPU環境、対象手話言語は未確定。

## 進める順序

1. 環境確認：OS、Python、GPU/VRAM、空き容量、入力動画の有無を記録する。
2. 入手：コードrevision、重みと付随ファイルの取得先、利用条件を確認する。
3. 再現：モデル別環境を作り、まず上流のサンプルまたは条件の合う動画1本で推論する。
4. 所感：実出力、セットアップの難しさ、処理時間、失敗、手直しした点を記録する。
5. 自前動画：同意済みの英語口パクや対象手話を数本試す。最初から大量収集しない。
6. 比較：同じ入力で候補を比較し、採用・保留・不採用と根拠を残す。必要に応じて定量評価を増やす。

## この段階の完了条件

- VSRの各候補について、実行手順・環境・出力・所感、または実行を阻む具体的な問題が残っている。
- VALLRは「音素まで動いた」と「文章化まで動いた」を区別し、prompt入力の可否を調べている。
- 手話候補は言語・認識単位（単語/連続系列）・語彙・重み入手性を整理し、試運転した候補の所感を残している。
- 再現できた候補は他メンバーが手順を追える。動かなかった候補も未検証/失敗と明示する。
- 最終的に実行確認できた候補から次に使うモデルを選ぶ。全候補が動かない場合は選定未完了とする。

## 今回作らないものと将来像

会議UI、WebRTC、部屋管理、字幕共有API、TTS、翻訳、アプリの共通契約は後の段階で設計する。
将来は入力方法の違いを字幕へ変換するインターフェースを作るが、その構築をモデル試運転の前提にしない。
当初の仕様書のMust要件や会議デモの完成条件は今回適用しない。
